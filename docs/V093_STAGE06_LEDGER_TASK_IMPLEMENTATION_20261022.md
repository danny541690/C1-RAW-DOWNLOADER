- 缺失身分包含來源、市場、資料集、證券、起訖日與原生單元；按證據雜湊去重。修復任務另綁輸入雜湊、處理器版本與規則版本。同一 owner、同一單元的版本任務不得並行。
- 領取須通過處理器版本證據登錄；領取具有到期時間與遞增 fence。過期程序不能提交結果；已解決缺口不因重複掃描而重開，其他待處理版本會取消。
- RAW 補抓必須先有預期單元證據、歷史請求次數證據。首次加三次重試合計最多四次，版本更新或中斷均不歸零。送出前先存請求意圖；重複 request_id 不會再取得送出許可。
- 未知 HTTP 結果須對帳；找到已存回應就重用，第四次已存回應仍可驗證結案；第四次失敗或未保存則維持耗盡。失敗紀錄保留原因、證據與當次 fence。
- 結案需 owner 回執、正確任務與版本身分、輸出雜湊與驗證證據雜湊，以及該缺失類型的檢查。RAW 回執須對得上已保存回應。基本 QA、解析、數值比對、PIT 各有不同結案條件。
- 這是回執契約驗證；數值比對及公開時點證據的實際產生與查證仍由 owner 接點負責，不能因帳本狀態變 RESOLVED 就宣稱整體資料通過 numeric/PIT 驗證。

## 正式自動修復還需完成的接點

1. 預期單元登錄：交易日、上市櫃期間、來源可提供日期、資料集適用範圍及原生回執；不能用月份缺檔直接認定市場資料缺漏。
2. 對回 3 筆舊版 unit_id 的原始收據及來源期間，再解除身分待對帳。
3. 各 owner 接入領取與回執：RAW 沿用原本來源順序、請求次數與單一下載責任；QA1 重驗；PRICE／FINANCIAL／CHIP 使用驗收過的版本重算。須具備 RAW 補抓、解析修正及失敗重試的端到端驗收。
4. 將真實輸出讀回、雜湊、數值／時點證據接入回執驗證；測試回執不能作正式資料合格依據。
5. 完成 owner 接點驗收後才啟用第六條常態排程與實際任務處理。目前 enabled=false、owner_replay_contracts_implemented=false、new_sources_enabled=[]。
