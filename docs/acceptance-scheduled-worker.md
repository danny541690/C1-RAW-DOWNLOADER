# JARVIS 自動驗收排程（候選實作）

使用一個每日統籌流程、三個並行內容工作與一次彙總，讓已實作的例行查驗由 Python／GitHub Actions 執行。程式沒有模型或 ChatGPT API 呼叫。這是能續跑的唯讀驗收工作，不是已完成八大組全部檢查的承諾。

## 工作與時間

每日台灣時間 02:17 排程（UTC cron `17 18 * * *`）；也可在 Actions 手動執行。GitHub 的排程為盡力執行，可能延遲，只有合併到預設分支後 schedule 才會生效。本候選 PR 本身不會啟用排程。

|工作|職責|每次上限|
|---|---|---|
|inventory|在已知 RAW 根目錄分頁盤點；未完成就續前次游標，完成後每日重新盤點|每片60次／90秒、每輪最多5片；整個job最多12分鐘|
|worker-0／1／2|依原件 package ID 的固定雜湊分成三份，讀回、核對遠端大小／MD5、計算SHA、核對登錄成員SHA、呼叫現有來源內容檢查器|每個工作8個原件包、128MiB已列舉大小、1000個內容單元、600秒處理迴圈；job最多18分鐘|
|summary|合併本輪三份結果，列出缺失、未知與待核|job最多3分鐘|

三份工作對 package ID 互斥；同一個包的多個成員在同一份工作處理、每輪只讀回一次。八大驗收是結果分類，不是必須開八條 cron。並行上限固定為3，避免因任意增加工作數造成重讀、限流與額外執行費用。個別網路呼叫仍可能耗時，job timeout 是最後的硬上限。

重跑同一個 GitHub run 的失敗工作時，僅替換該工作當輪同名 Artifact，持久斷點仍由專用 Git 分支保留；不同並行工作使用不同檔名，不互相覆蓋。彙總器核對 inventory、worker-0、worker-1、worker-2 四個身分；缺件、重複工作、未知報告格式、負值／布林計數、上游工作失敗或授權停等都不能算成本輪內容工作完成。完整盤點尚未就緒時，單獨顯示 WAITING_FOR_INVENTORY。

## 現有工作是否暫停

這個 PR 不修改既有下載／補正排程。新增流程只讀既有 Drive 原件與程式庫登錄表，不向 TWSE、TPEx、MOPS、FinMind、TAIFEX、TDCC、NDC 發出新的市場下載請求，也不改正式 RAW、品質任務或分析發布狀態。是否暫停其他工作，應按實際重複工作、寫入衝突及來源限流證據判斷，不因新增驗收而全部停掉。

## 輸入與適用範圍

預設使用 `reports/raw-register/20261027_v1/units` 的既有已下載紀錄；全歷史目標為2000～2026，但這份舊盤點不是核准歷史母體，也不是最新唯一原件全集。未下載旗標只保留待對帳，沒有變成自動重下載命令；遠端有但未在登錄表的原件，目前只完成metadata盤點，尚不自動猜測所屬資料集。補存版本、最新下載收據與核准母體的完整整併仍待實作，不能把此流程當成全庫已覆蓋。

盤點尚未完成時內容工作等待，不用不完整清單推定原件不存在。盤點是逐頁取得，不是原子時間點快照；每份原件下載後再次讀metadata，比對版本／大小／MD5，變更則保留待重讀。MD5只用於傳輸核對，實際成員另與既有SHA256登錄值比對。

## 斷點、重試與隔離

- 斷點以壓縮JSON保存在獨立的 `jarvis-acceptance-state/inventory`、`worker-0`、`worker-1`、`worker-2` 分支；不依賴可被淘汰的 Actions cache，也不寫入 main。分支只含這個工作的壓縮狀態。保存採快轉提交，競爭寫入會失敗，不強推覆蓋。
- 同一原件metadata、任務、原件SHA、來源相關檢查器與適用興櫃證據皆未變，就沿用已有部分內容結果。內容失敗也保留隔離，不在每次cron重跑相同錯誤。來源不相關的檢查器或興櫃證據變動，不使其他結果失效。
- 網路讀取最多跨次累計3次，每次至少間隔6小時。請求前保存次數；中斷不重設重試預算。超限需檢查原因或等原件metadata變更，不會無限循環。單筆內容錯誤不阻擋同包其他任務。
- 每次讀取原件前、每20筆內容結果及每個包結束保存本機與專用遠端分支斷點，保存失敗即停止繼續讀取；job結束即使發生錯誤也嘗試保存分支與30天Artifacts。硬中止時最多可能重做尚未遠端保存的當輪片段，不會因此關閉任務或重設已遠端記錄的讀取次數。
- `invalid_grant`／`invalid_client` 或讀取401會停止該工作繼續碰Google；修復授權後，在手動執行時勾選 `clear_auth_hold` 恢復。普通網路錯誤不冒充永久授權失效。程式不輸出或保存OAuth錯誤原文與憑證。
- 超大原件、壓縮展開超限、缺傳輸校驗、SHA衝突都留待人工／專用讀取器處理，不當成已驗通過。壓縮CRC僅在實際讀取的成員被檢查，沒有宣稱整包所有成員都已逐份讀取。

## 八大組的自動化界限

現有來源檢查器可以自動累積原件、日期、欄位與部分數值證據；完整歷史母體、全部欄位契約、真正獨立跨來源比對、PIT、更正版、全量還原及實際下游發布證據尚未齊備。缺檢查器或必要證據保持OPEN／BLOCKED，不由排程填入PASS。

本流程的摘要只表示本工作的已執行部分，不覆寫原先「0組完整、6組部分、1組未知、1組阻擋」的歷史進度表；正式發布核准範圍仍0。自動修補來源值、自動核准母體、自動關閉品質任務與正式發布均沒有接入。

## 啟用與驗證

1. 審查並合併 PR，確認既有三個 Google secrets 可用、GitHub token可建立上述專用狀態分支。沿用既有 `requirements-qa.lock`。
2. 一次性唯讀線上演練已完成，見 `reports/raw-acceptance/20261028_scheduler_live_readiness`。真實Google連線、分頁盤點、三份分工、QA專用分支與第二輪續跑均有實證；沒有啟用每日cron。這是小批操作驗證，不是全歷史資料驗收。
3. 每天由同一cron持續執行，不需要反覆在ChatGPT輸入「繼續」。GitHub的runner分鐘、儲存與Google服務配額仍各自計算，不能說完全沒有其他資源成本。

離線驗證：`python -m unittest discover -s tests -p 'test_acceptance_sched*.py'`、`python -m unittest discover -s tests -p 'test_acceptance_state.py'`，另以既有FinMind內容檢查器測實際格式接合。新測試驗斷點重啟、原件分工、相依失效、SHA／版本變更、重試上限、內容隔離與狀態分支競爭，沒有把軟體通過當資料全驗通過。

追加合併測試涵蓋：三個真正並行執行的離線工作，限制第一輪處理量後從壓縮斷點續跑，接上現有FinMind原生格式檢查器，保留一筆錯誤隔離，確認同包不跨工作重讀、原件不變、第三輪未變輸入不再讀取，最後以真實輸出的三份摘要彙總。遠端讀取適配器使用記憶體fixture，這些測試不等於正式Google連線或2000～2026全量資料驗收。

另有一次性線上流程 `.github/workflows/jarvis-acceptance-live-rehearsal.yml`，只在候選分支修改該檔或手動觸發時執行，沒有cron。2026-10-28已完成真實Google盤點與兩輪續跑：71,645筆檔案metadata、第一輪49個單元、第二輪沿用49個並追加38個；實際讀回的87個單元原件SHA未衝突。75個為部分內容證據、12個內容阻擋，不能把工作綠燈當87個驗收通過。日常流程的盤點片數預算已對齊這次實測，避免只有60個請求而讓當前約220請求的完整盤點分散到數日。
