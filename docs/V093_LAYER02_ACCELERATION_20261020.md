# 第二層轉換加速查核與第一批改善

## 結論

目前可直接改善的是每個小檔案周邊的 Drive 查找與進度報告寫入。
先降低這些開銷並量測各階段，再決定檔案合併或額外運算資源。
本批不改解析數值、原始資料、來源優先順序、處理憑證與內容雜湊規則。

## 查閱的公開原始資料

- Google Drive performance: https://developers.google.com/workspace/drive/api/guides/performance
  使用必要欄位與中繼資料批次請求降低連線開銷；media 上下載不支援 batch，
  批次中的子請求仍分別計算配額。
- Google Dataflow pipeline best practices:
  https://docs.cloud.google.com/dataflow/docs/guides/pipeline-best-practices
  可重用的初始化在批次層處理，批次化外部請求並控制並行。
- FIS Market Reconstruction 2.0:
  https://cloud.google.com/customers/fis/FIS-Market-Reconstruction-25B-Load-Test.pdf
  這是較早的金融資料平台原型案例，採合成 FIX 事件與大型雲端架構。
  第 4.5 節討論快取、減少非必要紀錄與批次初始化，第 4.1 節要求跨階段量測。
  原案例硬體與效能數字不適合直接外推本系統。
- Apache Arrow Parquet:
  https://arrow.apache.org/docs/python/parquet/parquet.html
  使用欄位投影、串流批次與本地檔案路徑；現有 ParquetWriter 已部分採用。
- DuckDB design:
  https://duckdb.org/why_duckdb.html
  欄式與向量化運算減少逐值處理成本，適合作為後續查詢/計算層候選。

## 已實作的低風險改善

1. 第二層工作使用 batch-local 正向檔案索引。每個父資料夾先分頁取得
   id/name/mimeType/size；已知名稱用 ID 讀取。新名稱仍重新查詢，避免把
   「尚不存在」快取到新檔案建立後。既存同名衝突維持阻擋。
2. 原始檔仍完整下載算 SHA；既有輸出仍讀取實際 bytes 核對；新輸出
   仍完整存檔讀回；每個輸入的處理憑證仍立即保存。
3. 較大的彙總報告改每 10 個輸入或 60 秒檢查點更新；遇到錯誤、時限
   及月份結束強制更新。中斷後從已持久保存的逐檔憑證重建報告。
4. 新增 wall time、Drive 請求數、下載位元組、原始下載、receipt 讀寫、
   解析、Arrow 編碼、Parquet 本地寫入、輸出上傳/讀回與報告寫入耗時。
   Drive put wall time 包含內部讀回，與部分 api timing 重疊，不能直接相加。

## 驗證與界限

合併套件本地 135 項通過。控制情境的 307 次相同資料夾中繼資料查找，
由 307 次網路 list 請求降為 1 次索引 list。307 個輸入的無時間推進情境，
彙總寫入由 308 次降為 32 次；真實情境另有 60 秒與錯誤觸發更新。
這些是請求數測試，並非已量到實際端到端倍速。

索引僅適用已由排程隔離的單一 writer，並在新工作重新建立；不跨工作
永久信任過期目錄。每次內容讀取的雜湊規則不變。

## 後續改善順序

- 先用新計量確認耗時占比和成功處理率，對剩餘工作量給出範圍估時。
- 若小檔開銷仍顯著，再以不可變 manifest 指向合併後的月/來源 Parquet
  分區，完整保留來源檔案/資料列血緣；舊檔不刪除、不直接混入 approved。
- 若 CPU 解析占比高，再對互不衝突的輸入採有界平行，按實測配置。
- DuckDB/Arrow 用於本地批次查詢與必要欄位運算；金融欄位須明確型別與
  單位，不以自動推斷取代資料契約。
- 首版盤後研究範圍與完整多年歷史資料庫分別驗收。首版不必等待十年
  RAW、所有第二層歷史分區或全部 443 指標完成。
