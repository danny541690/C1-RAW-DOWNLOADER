# C1 0.94｜架構比較、資源限制與修正決策
檢視日期2026-11-02。結論：保留既有Drive＋GitHub Actions＋Parquet/DuckDB的個人資料湖方向，先收斂治理與自動化入口，不建一套需要本人維護的法人級常駐叢集。

## 目標與可驗收條件
個人盤後市場資料庫，免費官方來源優先；使用者不寫程式，每日維護＋看盤研究60分鐘。需要可追溯、可重現、可標示缺失的資料；自動更新是部署目標，不代表本次整理後全部分析功能已上線。歷史資料用於驗證假說與風險，不能確認未來策略一定正確。

|對象與官方證據|值得採用的概念|C1的採用方式與限制|

|Man Group Arctic文章 [2]|時間序列版本追蹤與歷史快照|RAW不可變＋generation／release；不要求導入其整套儲存系統|
|World Bank DIME [3][4]|資料與行政檔案同步、程式Git版本、原始資料保護、可重現分析|Drive保存資料／文檔、GitHub保存程式及規則，保留血緣與還原測試|
|UK AQuA Book [5]|依風險安排QA、假設／決策／變更紀錄|關鍵行情／身分／PIT嚴格核對，探索性研究與正式發布分級|
|FinMind作者公開介紹／課程 [6][7]|佇列、分散worker、資料服務、監控與CI/CD|以現有短job＋CAS／checkpoint＋回執對應責任；不在短命runner上常駐broker|

這是根據公開方法為C1做的設計判斷，不是對法人私有資料架構的完整稽核；FinMind書籍全文未取得，不宣稱逐章讀過。

## 建議的簡化資料流
來源契約／官方發布 → 有限佇列與來源單寫worker → 不可變RAW與回執 → 標準Parquet與分層QA → Approved View → 指標／股票與債券研究 → 每日摘要及個人決策。控制層用GitHub任務／release與Drive manifest對應，兩者職責不互相覆蓋。資料層維持舊ID，文件層採0.94；新增配置必須明確指定資料根目錄ID，不依顯示路徑猜測。

DuckDB適合按需單工作節點查詢Parquet；不將一個Drive同步中的.db檔當多writer線上伺服器[8]。若未來真的需要多用戶、低延遲API或穩定服務SLA，再評估託管SQL／物件儲存，不先增加維運負擔。

## 低成本取捨與方案校正
採官方免費核心來源＋FinMind補缺，依策略依賴下載，不追求所有可抓資料。官方FinMind方案頁在2026-11-02列Free 300次/時、註冊600；699 Backer 1600次/時、81資料集；整日全標的下載列在Sponsor Pro [9]。因此先前「699一定一次下載全部市場全部資料」不能當規則；各端點權限、歷史起點、實際帳號quota要另驗。以上為當日頁面資訊，不保證未來方案不變。

不新增主機或付費訂閱；現有Drive／ChatGPT費用、Actions計費與實際儲存增長仍須當月核對。內部來源預算比方案上限保守是容錯設計。日常只抓到期新資料和已確認缺口，低優先回補按剩餘配額執行。無需要的盤中資料一律不收，避免容量和成本失控。
