# JARVIS 七來源完整閉環排程方案（2026-10-29）

狀態：設計／規格驗證候選，七個手動預覽workflow已產出；不是已接管下載修復的正式服務。現有排程未停用，新七條沒有cron、OAuth或寫入權限。規格及預覽不能冒充閉環已完成。

## 1. 最終配置：七條來源，各自完整閉環
|編號|來源|完整負責範圍|
|---|---|---|
|1|TWSE 證交所|上市行情、法人、融資券、估值等契約實際支援資料|
|2|TPEx 櫃買中心|上櫃對應資料；興櫃僅保存，不分析|
|3|MOPS 公開資訊觀測站|月營收、財報、公告與修訂；歷史路由獨立處理|
|4|TAIFEX 期交所|期貨／選擇權等已驗證來源目錄；歷史和最新快照分開|

|6|NDC 國發會|景氣與跨資產官方實際提供序列；完整來源包只抓必要新版本|
|7|FinMind|僅消化明確官方缺口，不做全市場歷史重抓、不自動升級付費|

每條均執行：最新收據對帳 → 既有原件檢查 → 判斷缺件／來源更新／解析錯誤 → 必要下載或校正 → 持久保存 → 遠端回讀SHA → 基本／數值／PIT分層重驗 → 更新任務、缺口與數字報告。批次之間不等待別的來源整月全部完成。

八大驗收是每條共用的規則目錄，不是第八條排程。跨來源比對採邏輯任務鍵指定唯一比對owner，依賴未齊就排隊，不讓兩條互相循環等待。FinMind若轉載同一官方來源，不構成獨立Golden。各條結束時更新自身分片報告；任一條可讀取七份報告產生帶時間戳的聯合視圖，不共寫同一大JSON。缺少或過期的來源報告標示UNKNOWN，不當作零。

- 月營收、季度財報、週股權分散、月景氣序列各按原生頻率建任務，不能硬造每日資料。
- 歷史證券母體、交易日、可用端點和適用區間需有證據。官方菜單未提供，不等於該歷史資料不存在。
- 新更新使用獨立watermark及有界佇列，不能重置歷史cursor。初始容量建議：70%歷史、20%到期修復／重驗、10%最新更新；無待辦可借用，量測後調整。
- 每條先對帳0.93成功收據再排工作，不重新下載已驗證原件，也不把舊缺件flag直接當下載命令。

## 3. 連續執行，消除刻意空等
- 初始每來源一個活躍工作，共最多七個，來源獨立concurrency，cancel-in-progress=false。
- 每批45分鐘軟預算、60分鐘job、90分鐘租約，每60秒heartbeat；原件包內分批處理，停止新任務並預留保存時間。
- 不採每輪8包的小上限；採時間、位元組、記憶體與供應商請求預算。大包串流／逐成員讀取，避免全包反覆解壓與無界記憶體。
- 批次保存成功、尚有可執行工作且來源未hold，立即workflow_dispatch下一批。不是45分鐘後再等一個小時。
- 每10分鐘看門狗只補啟動沒有活躍owner的來源；不重啟正在跑的工作。每次啟動綁定campaign generation；重複dispatch最多多一個空啟動，不能重做已領工作。
- 若待辦清空或只剩未到期／缺規則阻擋，不自我派送；後續資料更新、規則修正或冷卻到期才再做工作。
- 不用工作中斷後自動無限重開，也不用無限workflow_run串接。GitHub官方文件確認GITHUB_TOKEN的workflow_dispatch可觸發後續工作；生產接入需actions:write及來源owner/epoch驗證。平台排隊、交接、必要退避仍可能有間隔，不宣稱零等待。
- 最新同來源超過限流就減速，不能以多開排程繞過限流。GitHub、Drive共享配額採背壓。

## 4. 正確性與下載／校正
- 任務鍵：campaign、來源、市場、資料集、證券、內容起迄／報告期、來源契約版本。產物另綁RAW SHA、解析器／檢查器版本。
- 已有原件無可靠收據：先讀回重建證據，非直接來源重下載。同名異內容或SHA衝突隔離，保留雙方。
- 缺件：最新收據＋遠端讀回核對後，從實際支援的官方批量端點取得。來源更新：保存新版本，不覆寫舊原件。
- 解析或單位問題：保留原始bytes，只產生新解析版本；RAW保留原單位，展示金額依適用幣別／匯率契約統一億元。EPS／價格／股數不轉億元。
- 跨月回應完整父bytes保留，子分片按契約內容日期歸月並記父SHA，不把整包塞進結束月份。
- 初次＋最多追加3次=4次總來源嘗試，先持久記REQUEST_INTENT才HTTP，重啟不重設。未知意圖先對帳已存原件再決定續送；Drive傳輸恢復與來源嘗試分帳。
- 429尊重Retry-After，5xx／暫時斷線採有界退避；401／invalid_grant進AUTH_HOLD；格式／語意錯誤進CONTENT_BLOCKED；單一錯誤不擋其他工作。
- 空回應、404、非交易日、未發布、已查證零事件、來源歷史不支援分開；僅有可追溯證據的N/A才能列已確認例外，不補零、不偽造PIT。
- 來源補充保存官方缺口證據、定義、單位、頻率、公司與期間映射。FinMind原件留在FinMind來源樹；不得混入官方原件或自動關閉官方缺口。保守初始最多20次來源請求/批，還須服從實際帳號共享配額，這不是供應商保證額度。

## 5. 保存、鎖與進度
- 來源狀態各存jarvis-source-state/SOURCE分支，控制／請求預留不再七條搶同一main控制檔。移除舊main每請求控制提交前，先保留舊lease/fence語意並驗收。
- 任務owner/fence＋租約CAS阻擋過期工作寫回；來源單一寫者，輸出分區另有細粒度鎖。原件不可變，完成遠端回讀再寫成功收據。
- 每成功單元立刻保證原件與收據持久；游標每20單元或30秒保存，跨月及批次退出一定保存；續派送必須在保存成功後。
- 每輪歷史紀錄包含run_id、attempt、時間、程式SHA、原件版本、檢查器版本、請求／耗時／位元組、來源日期、修復前後結果。
- 數字同時呈現：核准應處理／候選待對帳、已檢查、新增下載、來源更新、已校正、重驗通過、已修復、已確認例外、內容阻擋、未檢查、尚待處理。檔案、包、單元、觀測值不得混加。
- 已下載不等於正確；基本QA不等於數值／PIT通過；已訪問月份不等於完整。分母未知時不報全庫百分比。
- 產物與進度不只靠30天附件；Git分支版本歷史＋Drive原件／收據為持久來源。存檔失敗即停該來源新請求，保留最後成功checkpoint。

## 13. V4：Git分支CAS後端與真實雲端協調預檢

新增v093_source_git_store.py，使用隔離來源分支與普通fast-forward push實作CAS，禁止force push；不同更新即使內容相同也使用唯一commit，避免舊revision相同內容被誤認為CAS成功。讀取不依賴共享FETCH_HEAD，操作不切換工作樹。網路／認證失敗與真正競爭拒絕分開，保存失敗不能繼續來源請求。狀態目前上限32MiB，正式全量佇列仍須分頁／分日期桶，不能直接裝入全部20萬候選。

新增一次性jarvis-source-control-live-preflight.yml：seed七個專用QA分支，十一個獨立GitHub worker寫入各自測試槽，再由另一個全新runner讀回全部來源。這項驗證使用真實GitHub保存／競爭／讀回，payload是合成控制資料，沒有市場HTTP、Google Drive或正式資料庫寫入。它不是第十二條正式來源排程，沒有cron。

本機合併87項與十一預覽YAML通過；正式遠端驗證結果以該workflow實際run為準，不提前宣稱成功。來源executor、真實Drive資料閉環、自動續派送的GitHub API接線、一次停舊切新與流量工期仍待驗收。
